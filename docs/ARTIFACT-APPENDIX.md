## A.1 Abstract

The artifact reproduces the paper's analytical result and its demonstrations on a live
Keycloak and Spring Security stack. The headline is a one-command run: sweep the DPoP proof
rate and observe replay rejected below about 17 req/s and admitted above 18, matching the
threshold `R* = N/S` read from Spring Security 6.5.5 source. Further probes show the
eviction budget is attacker-controlled and cross-tenant, that the admission boundary tracks
the product of rate and delay, and that the `iat` window is two-sided. The DPoP-versus-mTLS
latency comparison and hypotheses H1–H4 are not evaluated and no outcome is claimed for
them.

## A.2 Description and requirements

### A.2.1 Security and ethics

The artifact studies insecure behaviour and contains configurations that are weak by
design: the stock Spring Security default cache under study, and a certificate-binding
validator that fails open on purpose to demonstrate a silent failure. Neither is deployment
guidance; both are labelled in place. All stacks use throwaway credentials and PKI
generated at run time, bound to localhost. Nothing targets a third party.

### A.2.2 Access

Public repository, tagged release. Commit history carries the pre-registration ordering.

### A.2.3 Hardware

One x86-64 or arm64 machine. 4 CPU cores and 8 GB RAM are enough for the single-host runs;
the D2 three-replica stack is comfortable at 8 cores and 12 GB. About 5 GB disk for images.
No special hardware.

### A.2.4 Software

Docker with Compose, and `python3` with `httpx` and `cryptography`. `matplotlib` is optional
for the plot. Images are pinned: Keycloak 26.6.1, Spring Boot 3.5.5, Spring Security 6.5.5,
Redis 7, Envoy 1.35, Java 21.

### A.2.5 Benchmarks

None external. All inputs are generated by the harness.

## A.3 Set-up

### A.3.1 Installation

```
git clone <repo> && cd <repo>
python3 -m pip install httpx cryptography
```

Docker must be running. `reproduce.sh` builds images on first run.

### A.3.2 Basic test

```
RATES=16,18 REPEATS=1 ./reproduce.sh
```

About three minutes. Expected: the correctness suite passes, then the sweep reports 16 req/s
rejected and 18 req/s admitted, straddling the threshold.

## A.4 Evaluation workflow

### A.4.1 Major claims

- **C1.** Replay is admitted iff the honest rate exceeds `R* = N/S ≈ 17 req/s`. Below the
  crossover, rejected; above, admitted. Shown by E1.
- **C2.** At idle the cache enforces `jti` single use, the `iat` window edges, and the
  `htm`/`htu`/`ath` bindings. Shown by E1.
- **C3.** An attacker holding a stolen token evicts a victim `jti` himself, at idle, with
  self-signed proofs that each 401 on `jkt` but insert first. Shown by E2.
- **C4.** A neighbour's legitimate HTTP 200 traffic evicts a low-traffic client's `jti`,
  with no rejected request, because the cache is one JVM-wide instance. Shown by E3.
- **C5.** The admission boundary is the product `R·t ≈ N`: fixing `R` and sweeping the
  delay `t`, the crossover moves as `t* = N/R`. Shown by E4.
- **C6.** The `iat` window is two-sided (`iat ± S`), so a correct cache must retain a `jti`
  for `2S`, and the default is safe only below `N/2S ≈ 8 req/s`. Shown by E5.
- **C7.** With the default cache a proof replayed to a different replica is admitted at any
  rate; a Redis-shared cache rejects it everywhere and fails closed when Redis is down.
  Shown by E6.
- **C8.** A bearer token (C0) replays from any client; the same token bound with
  `cnf.x5t#S256` (M1) is admitted only over its bound certificate. Shown by E7.
- **C9.** With a lenient validator and broken or lossy certificate propagation, a token
  presented over the wrong certificate is accepted; the strict cells and the X1 control
  reject. Shown by E8.
- **C10.** The added nonce path refuses a nonce-less proof, issues one, accepts a proof
  carrying it, rotates on success, and rejects a verbatim replay. Shown by E9.

Not evaluated: the DPoP-versus-mTLS latency comparison and hypotheses H1–H4. The analysis
pipeline is validated on synthetic data only and makes no latency claim.

### A.4.2 Experiments

Times are planning estimates dominated by the one-time image build. Each experiment writes
the named results file.

| ID | Command | Output | Backs |
|---|---|---|---|
| E1 | `./reproduce.sh` | `single-host-validation/results/{sweep.json,correctness.txt}` | C1, C2 |
| E2 | `adversarial/attacker_flood.py` | `adversarial/results/attacker_flood.txt` | C3 |
| E3 | `adversarial/cross_tenant_eviction.py` | `adversarial/results/cross_tenant.txt` | C4 |
| E4 | `adversarial/t_sweep.py` | `adversarial/results/t_sweep.json` | C5 |
| E5 | `adversarial/iat_window_probe.py` | `adversarial/results/iat_window.txt` | C6 |
| E6 | `d2-distributed-cache/correctness/cross_replica.py --mode default\|redis --with-redis-outage` | `d2-distributed-cache/results/*.txt` | C7 |
| E7 | `baseline-and-mtls/test/assertions.py` | `baseline-and-mtls/results/assertions.txt` | C8 |
| E8 | `xfcc-silent-binding/test/test_xfcc.py` | `xfcc-silent-binding/results/xfcc-outcomes.txt` | C9 |
| E9 | `d4-nonces/client/nonce_client.py` | `d4-nonces/results/nonce-flow.txt` | C10 |

E1 runs from the repository root; the rest need their own stack up first (see each
directory's README) and use loopback-bound ports, so run one at a time. After E1,
`python3 single-host-validation/check_results.py` verifies the run against the model and
reports host-too-slow (exit 2) separately from a model mismatch (exit 1).

Reference outputs for all experiments are committed under the same `results/` paths, so the
claims can be checked without re-running.

## A.5 Reusability

The statistical pipeline in `measurement-matrix/analysis/` is independent of the stacks and
has 145 tests (`pytest measurement-matrix/analysis`). It reads HdrHistogram, wrk2, and k6
output and is documented for reuse in the eventual latency study. It is validated on
synthetic data only.
